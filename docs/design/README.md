# Дизайн-код Slooop · v1
Для любого изменения Android UI. Одно место, куда смотреть перед вёрсткой и на ревью. База сверена с 3.2.89. Эти правила описывают продукт Slooop. Они не утверждают, что каждое наше решение обязательно по спецификации Google.

## 1. До написания кода
Опишите действие пользователя одним предложением. Назовите семейство из таблицы, найдите существующий экран с тем же поведением и посмотрите его при включённом и выключенном оформлении. Перед вводом нового публичного компонента покажите, почему ближайший существующий не подходит. Принятый образец меняется одной правкой в этом документе и в общем компоненте. Не копируйте весь экран-образец. Исправляя общий компонент, перечислите как минимум двух его потребителей, если они есть, и проверьте их.

| Что делает человек | Что показываем | Отправная точка в коде |
|---|---|---|
| Нажал на значок статуса поста | Короткое объяснение рядом со значком; закрытие назад или снаружи. При недоступности такого показа сохранить рабочий прежний путь. | `StatusExplanationPopup`, пример «Не поднимает тред» |
| Читает справку, например о PIN | Заголовок по теме, короткие смысловые абзацы, одна текстовая кнопка «Закрыть». Без огромной заливки у единственного действия. | `MotionDialogBuilder.standard` / стандартный контент; утверждённый образец справки о PIN — отдельный пакет |
| Принимает решение, включает передачу или удаляет данные | До действия назвать объект и последствие. Два ясных действия: «Отмена» и «Удалить», «Включить» или другой точный глагол. Закрытие ≠ согласие. | Стандартный диалог, для разрушительного действия — `MotionDialogBuilder.standard(context, true)`; сохранить исходные обработчики |
| Меняет одно значение, выбирает из короткого списка | Стандартный выбор или поле, текущий вариант отмечен; «Отмена» не записывает изменение. | `ui/preference/core`, `InterfaceAppearance.modalChoiceRow`, `TextInputAppearance` |
| Пишет выражение, задаёт область применения и проверяет результат | Экран редактора с заголовком и действием сохранения; второстепенные секции можно свернуть. Не помещать весь сценарий в маленькое подтверждение. | Продвинутый редактор автоскрытия из отдельного пакета. Быстрый фильтр — самостоятельный сценарий. В полноэкранном редакторе «Режим скрытия» — единое поле выбора: подпись, текущее значение и стрелка. Нажатие на всю поверхность открывает список с одним выбранным вариантом. |
| Листает настройки, меню, каталог | Один визуальный ритм в пределах типа строк. Название, при необходимости краткое пояснение; выбор виден и без цвета. | `InterfaceAppearance.settingsRow / menuRow / serviceRow`, `DrawerAppearance` |
| Пишет пост, прикрепляет файл, решает капчу | Один главный следующий шаг; кнопки остаются доступны с IME, информация о вложении принадлежит редактору/вложению. | `PostingFormAppearance`, `PostingImeMotion`, `AttachmentMediaTile`; отдельная настройка формы постинга |
| Смотрит или редактирует медиа, вводит PIN | Сохранить известные жесты, контент и специализированную геометрию. Стандартные цвета/типографику применять с учётом локального компонента. | Роли `InterfaceAppearance.media…`, компоненты галереи, плеера, редактора и экрана блокировки. Не менять системный биометрический prompt. |
| Ждёт результат или исправляет ошибку | Состояние рядом с объектом; показывать проверяемый результат. Если есть действие — назвать его («Повторить»). Важная ошибка не должна успеть исчезнуть до чтения. | `InterfaceAppearance.serviceState / serviceErrorState / standardLoading`; для файла — компонент вложения. |

## 2. Тема, шрифт, размеры
- Цвета получает `ThemeEngine`. Для стандартных поверхностей используем роли `AppearanceColors` и фасад `InterfaceAppearance`: фон с читаемым текстом (`surface / onSurface`), пояснение (`onSurfaceVariant`), главное действие (`primary / onPrimary`), ошибки — семантические роли. Проверяем светлую, тёмную, пользовательскую и AMOLED при наличии. Цвет скриншота не константа для всех тем. Фото, образцы палитры, пользовательские цвета постов — данные; не перекрашивать их.
- Используем `AppearanceTypography.Role`: заголовок обычного диалога `TITLE_LARGE` (22/28), основной текст `BODY_MEDIUM` (14/20), кнопка `LABEL_LARGE` (14/20), параметры в sp. Не отключать пользовательский шрифт/масштаб ради совпадения со скриншотом.
- `AppearanceShapes` уже содержит интервалы 4/8/12/16/24 dp, min высоту строк 56/64 dp для настройки без/с описанием и 48/56 для служебной строки без/с метаданными. Это минимумы: длинная надпись растёт по высоте. 48 dp — ориентир для зоны нажатия; визуально сам знак может быть меньше. В левом меню согласованная строка — 48 dp.
- Главный список «Настройки», только при включённом новом интерфейсе: обычная строка без карточки, минимум 56 dp, ведущая иконка 24 dp, отступ от начала строки и интервал от рамки иконки до названия — по 16 dp. Иконки одноцветные, из роли `onSurfaceVariant`, строка нажимается целиком. У шапки остаётся цвет темы, на списке разделов она не отбрасывает тень. Поиск, вложенные экраны и классика сохраняют свои правила.
- Наружный отступ принадлежит ровно одному контейнеру. Для пользовательского тела стандартной формы см. `CompactDialogUi.markForm / prepareForm`. Для окна с клавиатурой — `DialogFormInsets`, где это уже предусмотрено. Не суммировать системный IME inset и такой же padding у дочерней формы.
- Скругление определяется типом поверхности: диалог и превью имеют разную задачу. Сохранить согласованные 2 dp на миниатюре видео. Не применять радиус диалога ко всем вложениям. При сопоставлении с макетом измерять край видимой поверхности отдельно от зоны нажатия.
- В классической шторке счётчик избранного при обычном шрифте — 32 × 24 dp по центру области нажатия 48 × 48 dp. Размер плашки не зависит от высоты строки; при увеличении шрифта она может вырасти под текст. У счётчика Material 3 свои размеры в `DrawerStyle`.

## 3. Поведение и текст — часть компонента
- Контрол показывает состояние даже без цвета (галочка, подпись, значок); кнопка без подписи получает понятное доступное имя, разделы — правильный порядок фокуса. Скрытый контрол не принимает нажатия. При IME клавиатура не перекрывает главное действие.
- Анимация объясняет изменение того же объекта. Один владелец изменения геометрии; прерванный жест возвращает корректное состояние. Использовать `InterfaceMotion` и существующий компонент сценария. При выключенных анимациях конечное состояние доступно сразу. 85 мс в `ReplySwipeOverlapSpec` — решение только для свайпа ответа, не универсальный тайминг.
- Заголовок называет предмет или решение. Подпись под настройкой нужна только когда объясняет последствие или ограничение, которого не видно из названия. Выбор из двух вариантов должен быть однозначен без чтения справки. Название кнопки — результат нажатия.
- Пример правки для справки о PIN: «Восстановления забытого PIN нет» → «Забытый PIN восстановить нельзя». Содержательные ограничения сохраняем. В согласиях и предупреждениях об удалении главный риск, адресат и момент действия видны **до** подтверждения. Не заменять согласие всплывающей подсказкой. Проверять русские и английские ресурсы вместе.
- Нельзя показать «Найдено совпадение» до ввода примера или «Готово» до результата. У ошибки написать, что исправить, и оставить введённое на месте.
- Сохранять политику защищённого окна, состояние после поворота, Back, доступность отмены и обработчики сохранения. Дизайн-код сам не разрешает менять хранение данных или поведение операции.

## 4. Переключатели и исключения
Общая презентация Material подключена к обеим сборкам через `distribution/material3`. Настройки оформления, формы постинга, плеера, компактных окон, IME, Predictive Back имеют разный смысл. Область действия сверяйте с `Preferences` и вызывающим экраном. Например, два согласованных новых экрана привязаны к существующему `experimental_compact_dialogs` (default false); не превращать его в выключатель всего интерфейса. Не менять значения по умолчанию и не сбрасывать пользовательский выбор ради редизайна. Не подменять глобальную тему.
Исключения: системный выбор файла и биометрия, визуализация контента, просмотр шрифта как образца, явно сохранённый legacy-режим. Для нового прямого конструктора диалога нужна конкретная причина, действие общего компонента, которое мешает, и сценарий визуальной проверки. Пометка в коде ограничена одним вызовом; обзор — в PR. Само слово «экспериментальный» не объясняет исключение.

## 5. Критерий готовности
1. Указать семейство, используемый компонент, экран/точку входа и реально затронутые режимы. Исправлять причину в общем компоненте, только если она действительно общая.
2. Для первого внедрения — одна пара «до/после» на одном устройстве, теме, масштабе и состоянии, с тестовыми данными. Для защищённых окон — безопасный демонстрационный экран или ручная отметка, не отключать защиту ради скриншота.
3. Минимальная ручная проверка: светлая и тёмная тема; узкая ширина (пример 320–360 dp) и крупный системный шрифт; видны и нажимаются все действия. Для формы — IME, Back, поворот и сохранность набранного; для управления жестом — медленно, быстро, прерывание и выключенные анимации. Проверить OFF/ON соответствующего флага. Системные и пользовательские шрифты, AMOLED, TalkBack и обе сборки распределить по затронутым сценариям. Не объявлять непроверенное проверенным.
4. Для статического контроля см. `tools/design/audit.py`. Он не оценивает красоту, безопасность или доступность. Фиксировать результат визуальной проверки отдельно: «не проверено / воспроизведено / исправлено и проверено / осознанное исключение» с версией. Экраны без записи остаются непроверенными.
5. Смена правила: изменение в этом файле, обновление общего компонента при необходимости, перечень затронутых семейств и проверка эталонов. Исторические документы в `docs/` дают контекст; фактические source sets и переключатели берём из текущего дерева.
